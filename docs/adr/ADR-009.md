# ADR-009: Database-Only Feedback Validation and Duplicate Detection

- **Status:** Accepted
- **Current profile:** ADR-011 defines normalized comparison (case, outer whitespace, repeated internal whitespace), SMTP delivery/retry, and 30-day feedback retention.
- **Date:** 2026-11-12
- **Project:** University Transport Information Portal
- **Related drivers:**
  - **ASR-09 — Feedback anti-abuse:** Feedback submissions require a honeypot field and rejection of content-identical duplicates within a trailing 10-minute window. IP-based limiting is explicitly excluded.

## Context

The portal allows students and the public to submit feedback. The feedback functionality must include basic anti-abuse protection without introducing unnecessary external dependencies.

Two validation requirements must be enforced:
- Submissions with a populated honeypot field must be rejected.
- Content-identical submissions within the trailing 10-minute window must be rejected.

IP-based limiting is explicitly excluded. The architecture must determine whether duplicate detection should be handled through the database or an external spam-detection service.

## Options considered

| Option | Advantages | Disadvantages |
|---|---|---|
| Database-only duplicate check at write time | Avoids external dependencies and keeps duplicate detection within the existing backend and database | Requires a database check against recent submissions |
| Third-party spam-detection service | Provides an external spam-detection capability | Adds an external dependency disproportionate to a narrowly-scoped form |

## Decision

Adopt **database-only duplicate detection with API-layer honeypot validation**.

- The Feedback module owns feedback submissions, honeypot validation, and duplicate-window detection.
- The API layer must reject submissions when the honeypot field is populated.
- The database must be checked at write time for content-identical submissions within the trailing 10-minute window.
- Content-identical duplicates within that window must be rejected.
- IP-based limiting must not be implemented.
- No third-party spam-detection service will be introduced.

## Rationale

A third-party spam-detection service adds an external dependency disproportionate to the narrowly-scoped feedback form.

Database-only duplicate detection keeps the validation process within the existing backend and relational database. Combining this with API-layer honeypot validation satisfies the stated anti-abuse requirements without introducing another service dependency.

The selected approach also preserves the modular monolith's responsibility boundaries by keeping feedback validation and duplicate detection within the Feedback module.

## Consequences

### Positive
- No third-party spam-detection dependency is required.
- Honeypot validation is handled at the API layer.
- Duplicate detection uses the existing relational database.
- Feedback anti-abuse behavior remains within the Feedback module.
- The implementation follows the explicit exclusion of IP-based limiting.

### Negative
- The backend must perform a database check when processing submissions.
- Duplicate detection requires access to recent feedback submissions.
- The Feedback module must correctly implement the trailing 10-minute comparison window.

### Risks
- Incorrect duplicate comparison logic could allow content-identical submissions through.
- Incorrect time-window handling could reject submissions outside the required window or accept duplicates within it.
- Database query performance could become a concern if feedback volume grows significantly.

### Revisit when
- Database-only duplicate detection is demonstrated to be insufficient for the feedback anti-abuse requirement.
- A new ASR-based justification supports introducing additional anti-abuse infrastructure.

## Verification

- Verify that the feedback submission API requires a honeypot field.
- Test that submissions with a populated honeypot field are rejected.
- Test that content-identical submissions within the trailing 10-minute window are rejected.
- Test that content-identical submissions outside the trailing 10-minute window are not rejected by this duplicate-window rule.
- Verify that duplicate detection occurs against recent database submissions at write time.
- Verify that IP-based limiting is not implemented.
- Confirm that feedback validation and duplicate-window detection are owned by the Feedback module.
- Confirm that no third-party spam-detection service has been introduced.

## AI-agent instruction

Perform database-only duplicate detection at write time and reject content-identical submissions within the trailing 10-minute window. Do not introduce IP-based limiting or a third-party spam-detection service. Keep feedback submissions, honeypot validation, and duplicate-window detection within the Feedback module. Do not add external anti-abuse dependencies without an ASR-based justification and explicit approval.
