# ADR-001: Adopt a Modular Monolith

- **Status:** Accepted
- **Current profile:** ADR-011 supplies the selected technology profile; this ADR's modular-monolith decision remains in force.
- **Date:** 2026-11-12
- **Project:** University Transport Information Portal
- **Related drivers:** ASR-01 (published information must be visible within 5 seconds under the defined baseline workload); ASR-03 (draft/publish separation must prevent unpublished data from reaching students); ASR-04 (offline caching and synchronization require coordinated client and backend behavior); CON-01 (prohibits unnecessary integrations and infrastructure, including separate deployable microservices).

## Context

The University Transport Information Portal must provide public access to departure information, schedules, and announcements while allowing Transport Management and designated administrators to manage and publish transport information. The architecture must support a baseline of 500 concurrent users and 2,000 scheduled departures, with at least 95% of publication operations becoming visible within 5 seconds (ASR-01).

The system also requires strict separation between draft and published transport data (ASR-03), alongside support for stale, offline, and service/data outage states (ASR-04). These requirements introduce complexity in data management and coordination between system components.

The architecture should maintain clear business-module responsibilities without introducing unnecessary deployment and operational complexity. Recovery objectives (ASR-05) also favour an approach that keeps deployment, backup, and recovery manageable.

## Options considered

1. **Microservices:** Independently deployed services with separate deployment pipelines. Supports independent scaling and deployment, but introduces distributed-transaction, service-discovery, and multi-pipeline overhead that is not justified at the current scale.

2. **Modular monolith:** One deployable backend application with enforced internal module boundaries. Provides separation of business responsibilities while keeping deployment and backup/recovery manageable. Modules must deploy together, and boundaries require code organization and review rather than network isolation.

3. **Unstructured monolith:** One application without enforced internal module boundaries. Faster to start, but risks coupling between responsibilities that could undermine draft/publish separation and audit-history requirements.

## Decision

Adopt a **modular monolith** consisting of:

- A public-facing PWA client.
- A separate Admin Web App.
- One backend application with clearly defined logical module boundaries.
- A relational database as the system of record.

The backend shall remain a single deployable application. Business responsibilities, including Transport Data, Announcement, Feedback, Audit, Authentication, and Reporting, shall maintain their own boundaries in code.

Both frontend clients shall communicate exclusively through the backend API. Neither client shall access the database directly. A module must not directly access another module's private database tables or internal implementation.

## Rationale

The modular monolith provides an appropriate balance between separation of concerns and operational simplicity.

The current scale (500 concurrent users baseline and a small number of privileged roles) does not justify microservices. Their additional service-discovery, distributed-transaction, and multiple-deployment-pipeline complexity would work against ASR-05's recovery objectives, which are simpler to meet with a single system of record.

A modular monolith retains manageable deployment and backup/recovery while allowing each business responsibility to own its boundaries in code.

It also accommodates the intrinsic data-model complexity introduced by draft/publish separation (ASR-03) and audit history (ASR-06), without introducing additional deployment complexity.

An unstructured monolith was not selected because insufficient module separation risks coupling that undermines these requirements.

## Consequences

- **Positive:** A single backend deployment keeps deployment and backup/recovery manageable. Clear module boundaries support maintainability and separation of business responsibilities. The architecture avoids unnecessary distributed-system complexity.

- **Negative:** All backend modules must deploy together. Independent module deployment and scaling are not supported by this decision. Module boundaries depend on code organization and review rather than network isolation.

- **Risk:** Module boundaries may erode over time if developers introduce direct dependencies on other modules' private internals or database tables. This could undermine draft/publish isolation and audit responsibilities.

- **Revisit when:** Independent scaling or deployment of a specific module becomes a demonstrated requirement. Any change must be supported by an architectural justification based on the relevant ASRs.

## Verification

1. Review the backend directory and module structure to confirm that business responsibilities have clearly defined boundaries.
2. Verify that both the Public PWA and Admin Web App communicate only through the backend API and never query the database directly.
3. Inspect module dependencies and reject direct access to another module's private database tables or internal implementation.
4. Verify that the implementation preserves a single deployable backend application.
5. Confirm that no separate deployable microservices, Kafka, Kubernetes, or other prohibited infrastructure has been introduced without an ASR-based justification and explicit approval (CON-01).
6. Review automated tests covering:
   - Publish-to-visible latency under load.
   - Draft/publish isolation.
   - Offline, stale, and service/data outage client behavior.
   - Audit recovery correctness.
   - Feedback duplicate-detection behavior.
7. Confirm that the architecture preserves the draft/publish separation and audit-history responsibilities regardless of deployment structure.
