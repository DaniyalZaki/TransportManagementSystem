# ADR-004: Synchronous Cache Invalidation for Publish Propagation

**Status:** Accepted
**Current profile:** ADR-011 selects a single-worker in-process cache. A multi-worker deployment requires a new shared-cache decision.
**Date:** 2026-11-12
**Project:** University Transport Information Portal

## Related drivers

- **ASR-01 — Publish-to-visible latency:** Published information must be visible/retrievable within 5 seconds at the 95th percentile, under a baseline of 500 concurrent users and 2,000 scheduled departures.
- **ASR-02 — Urgent-change propagation:** Confirmed urgent operational changes must be live no later than 1 minute after confirmation.

## Context

The portal must make published transport information available quickly to students and the public. It must also ensure that urgent operational changes become live within one minute after confirmation.

The architecture must balance read performance with reliable propagation of newly published information. In particular, a cache must not continue serving outdated information after a publish operation has completed.

The main decision is how clients and the backend should propagate published changes while meeting the latency requirements.

## Options considered

| Option | Advantages | Disadvantages |
|---|---|---|
| Client polling only | Simple approach without additional server-side infrastructure | Latency is limited by the client's polling interval |
| Server push (WebSocket/SSE) | Can communicate changes to clients quickly | Adds persistent-connection overhead not otherwise required |
| Backend cache invalidated synchronously on publish | Subsequent requests return fresh data without additional push infrastructure | Requires cache invalidation to be coordinated with publishing |

## Decision

Adopt a **cache layer in front of hot reads, invalidated synchronously inside the publish transaction**.

- The cache is a performance aid, not a source of truth.
- Publishing transport data or announcements must synchronously invalidate the relevant cache entries.
- Cache invalidation must occur within the publish transaction, not after a delay.
- Subsequent requests must return fresh published data.
- Do not introduce client polling as the sole propagation mechanism or add server-push infrastructure without an ASR-based justification.

The specific cache technology is not yet decided and must be confirmed before implementation.

## Rationale

Client polling alone is latency-bound by the client's polling interval. This makes it less suitable for meeting the publish-to-visible requirement.

Server push through WebSocket or SSE could provide faster notification, but it introduces persistent-connection overhead that is not otherwise required by the system.

Synchronous cache invalidation provides a simpler approach: once publishing completes, subsequent requests can retrieve fresh data without relying on additional push infrastructure.

This supports both the 5-second publish-to-visible target and the one-minute urgent-change requirement while keeping the architecture manageable.

## Consequences

### Positive
- Hot reads can benefit from a cache layer.
- Subsequent requests return fresh data after publishing.
- The approach avoids additional server-push infrastructure.
- Synchronous invalidation supports the publish-to-visible and urgent-change latency requirements.

### Negative
- Publishing must coordinate cache invalidation with the publish transaction.
- Cache invalidation logic must correctly identify relevant entries.
- Cache technology remains an implementation decision to be confirmed.

### Risks
- Delayed or incomplete invalidation could cause outdated information to remain visible.
- Incorrect cache behavior could undermine the required propagation latency.
- Treating the cache as a source of truth could compromise data correctness.

### Revisit when
- Contention or observed latency demonstrates that the shared publish pipeline or synchronous invalidation is insufficient.
- A specific ASR-based requirement justifies introducing additional propagation infrastructure.

## Verification

- Verify that the cache is invalidated synchronously within the publish transaction.
- Test that subsequent requests return fresh published data after a transport-data publish.
- Test that subsequent requests return fresh published data after an announcement publish.
- Measure publish-to-visible latency under load against the 5-second target at the 95th percentile.
- Verify that confirmed urgent operational changes become live within 1 minute.
- Confirm that the cache is used only as a performance aid and is never treated as the source of truth.
- Test that no stale or draft content is served after the publish transaction.
- Confirm that no additional push infrastructure is introduced without an ASR-based justification.
