# ADR-014: Protect Public API Capacity at the Deployment Edge

- **Status:** Accepted
- **Date:** 2026-11-22
- **Project:** Uzair Transport Service
- **Related drivers:**
  - **ASR-01 — Publish-to-visible performance:** Published transport information must be visible within 5 seconds at the 95th percentile for the defined 500-concurrent-user baseline.
  - **ASR-04 — Public availability:** The Public PWA must distinguish a service/data outage from offline use and show retained cached information for up to 24 hours.
  - **ASR-05 — Recovery:** Production operation must support the stated recovery objectives.

## Context

The Public PWA exposes unauthenticated read endpoints. A surge in public traffic, a slow-client connection flood, or abusive read traffic can exhaust the FastAPI worker's request capacity or PostgreSQL connections. Before this decision, the architecture defined client-side outage handling but did not define server-side admission control or overload behavior.

The approved deployment remains one FastAPI worker with an in-process read cache. The worker cannot be multiplied safely without a reviewed shared-cache and cache-invalidation decision. The system therefore needs a way to reject excess work before it consumes the worker or database, while preserving a clear fallback for users.

## Options considered

| Option | Advantages | Disadvantages |
|---|---|---|
| Expose the FastAPI worker directly | Lowest deployment effort | Slow or excessive connections can consume application and database capacity, causing a broad outage |
| Add application-only limits | Keeps controls in the backend process | Overload reaches the worker before it can be rejected and competes with application capacity |
| Put a deployment edge in front of the API | Rejects excess or unhealthy traffic before it reaches the worker and provides health-aware routing | Adds production deployment configuration and operational monitoring |

## Decision

Use a production deployment edge - a reverse proxy or load balancer - in front of the backend API.

- It terminates client connections and forwards traffic only to a healthy FastAPI instance, using the existing unauthenticated `/health` endpoint for liveness and readiness checks.
- It enforces finite connection, request, and idle timeouts; maximum request-body sizes; and a bounded pending-request queue.
- It applies configurable per-client rate limits to unauthenticated public **read** endpoints only. The limits must not apply to the feedback endpoint, because the approved feedback policy excludes IP-based limiting.
- When a configured limit or queue capacity is reached, the edge returns a prompt `429 Too Many Requests` or `503 Service Unavailable` response with `Retry-After` where applicable. It must not hold requests until the FastAPI worker or PostgreSQL connection capacity is exhausted.
- The backend database connection pool has a configured upper bound that remains below PostgreSQL's safe connection capacity. The precise limits are deployment configuration and must be selected from load-test evidence rather than committed as fixed values in application code.
- The Public PWA retains its existing outage behavior: it shows an outage warning and the original synchronization timestamp with cached core data when available, or an unavailable message on first use.

This ADR does not add multiple FastAPI workers, a shared cache, CDN/API response caching, a separate deployable service, Kubernetes, or another database. Edge caching of public API responses needs a separate decision because publishing must synchronously invalidate every cache that can serve published data.

## Rationale

Admission control at the edge protects the limited capacity that matters most: the single application worker and the PostgreSQL connection budget. Prompt rejection is preferable to allowing a backlog to grow until ordinary readers, publishers, and health checks all time out.

The PWA already has the required user-facing failure mode. Pairing that fallback with explicit server-side overload handling turns an overload from a full service collapse into a visible, bounded outage for users who do not yet have cached data.

Keeping the values configurable avoids guessing production limits before the hosting platform, instance size, PostgreSQL capacity, and measured traffic are known.

## Consequences

### Positive

- Excess public-read traffic is rejected before it consumes all application or database connections.
- Health checks allow unhealthy backend instances to stop receiving new requests.
- Users with cached core information retain a labelled, time-stamped view during an overload outage.
- The design remains compatible with the single-worker cache decision.

### Negative

- A production reverse-proxy/load-balancer configuration and monitoring are required.
- Some users receive a temporary `429` or `503` response during a surge rather than waiting indefinitely.
- Limits need review as observed traffic and capacity change.

### Risks

- Limits that are too low may reject legitimate readers; limits that are too high may not preserve capacity.
- A misconfigured health check can withdraw healthy capacity or route traffic to an unhealthy backend.
- Edge response caching added without synchronous invalidation could violate publish-to-visible requirements.

### Revisit when

- Load testing shows the single worker cannot meet the approved baseline with the selected edge controls.
- Sustained demand demonstrates that multiple backend workers are required. That change requires a reviewed shared-cache and cache-invalidation decision.
- Public API response caching is proposed. It requires a reviewed invalidation design.

## Verification

- Load-test public reads at the approved 500-concurrent-user/2,000-departure baseline and record latency, error rate, worker saturation, and database connection use.
- Test traffic above the configured queue and rate limits. Confirm excess requests receive prompt `429` or `503` responses and do not exhaust the database pool.
- Make the backend health endpoint fail in a test environment and confirm the edge stops forwarding new traffic to it.
- Confirm a PWA with a valid cache shows its retained data, original timestamp, and a service-outage warning after an overload response.
- Confirm a first-use PWA presents an unavailable message after an overload response and does not show an empty schedule as current.
- Confirm feedback remains outside the public-read rate-limit rule and still follows its approved honeypot and duplicate-detection policy.
- Confirm no second FastAPI worker, shared cache, additional database, or public API edge cache has been introduced through this decision.

## AI-agent instruction

> For production deployment, place a health-checked reverse proxy or load balancer in front of the single FastAPI worker. Bound connection/request/idle timeouts, request size, pending requests, and PostgreSQL connection-pool use. Apply configurable per-client rate limits only to unauthenticated public read endpoints; do not apply IP-based limits to feedback. Reject excess requests promptly with `429` or `503` and preserve the Public PWA's approved outage-cache behavior. Do not add multiple workers, a shared cache, edge API caching, Kubernetes, a separate service, or another database under this ADR. Any multi-worker or public-response-cache change requires a separate reviewed decision.
