# ADR-003: Adopt Versioned Records for Draft and Published Data

**Status:** Accepted
**Current profile:** ADR-011 adds named atomic change sets, stale-draft rebase, 30-day draft expiry, 30-day whole-change-set recovery, and post-retirement physical deletion.
**Date:** 2026-11-12
**Project:** University Transport Information Portal

## Related drivers

- **ASR-03 — Draft/publish separation:** Route, schedule, and assignment edits must be saved as drafts and require a separate publish action. Students must never see unpublished drafts.
- **ASR-06 — Audit history and recovery:** Edits and publications must be retained in an auditable history for 30 days with actor attribution. Recovery is limited to previously published data, not drafts.

## Context

Transport Management and designated administrators must be able to edit routes, schedules, and assignments without immediately exposing those changes to students and the public.

The system must distinguish draft data from published data. Public read operations must return only published versions, while the system must retain edit and publication history for 30 days and support recovery of previously published versions.

The architecture must therefore provide a data model that enforces draft/publish separation while supporting version history and recovery.

## Options considered

| Option | Advantages | Disadvantages |
|---|---|---|
| Single table with a status flag | Simple data model | A missed status filter risks exposing drafts through public reads |
| Fully separate draft/published tables | Clear physical separation between drafts and published data | Duplicates schema and requires explicit publish-sync logic |
| Event-sourced model | Fits audit and history requirements | Adds more complexity than this domain requires |

## Decision

Adopt **versioned records per entity**, using a `status` and `version` discriminator.

- Draft and published versions are represented as versioned records.
- Public read operations must be restricted to published-version rows only.
- Draft/publish separation must be enforced at the data layer.
- Publishing promotes a draft to a published version, creates a new version, writes an audit entry, and invalidates relevant cache entries synchronously.
- Recovery may target only a previously published version, never a draft.

## Rationale

A single table with only a status flag risks exposing drafts if a public query misses the required filter. Fully separate draft and published tables provide separation but duplicate schema and require explicit synchronization during publishing.

Event sourcing can support audit requirements, but it introduces more complexity than this domain requires.

Versioned records using a `status` and `version` discriminator provide the selected balance. They support draft/publish separation and version history without adopting a more complex event-sourced model.

The draft/publish split and audit trail introduce data-model complexity regardless of the deployment style. This complexity is intrinsic to the requirements.

## Consequences

### Positive
- Draft and published versions are represented explicitly.
- Public reads can be restricted to published-version rows.
- Version history supports the audit and recovery requirements.
- The model avoids duplicating the schema across separate draft and published tables.
- The approach avoids the additional complexity of event sourcing.

### Negative
- Data queries and publishing logic must account for both status and version.
- The data layer must consistently enforce published-only public reads.
- Publishing requires version promotion, audit writing, and cache invalidation.

### Risks
- A public read path that does not enforce the published-version restriction could expose drafts.
- Incorrect recovery logic could restore a draft instead of a previously published version.
- Incorrect version handling could undermine the separation between draft and published data.

### Revisit when
- The versioned-record model cannot reliably satisfy draft isolation or audit/recovery requirements.
- A reviewed, ASR-based justification supports adopting a different data model.

## Verification

- Verify that route, schedule, and assignment edits are saved as drafts.
- Verify that a separate publish action is required before changes become publicly visible.
- Test that public read operations return only published-version rows.
- Test draft/publish isolation, including attempts to access drafts through public read paths.
- Verify that publishing creates a new version and writes an audit entry.
- Verify that recovery can target previously published versions only, never drafts.
- Test publish-to-visible latency under load and audit recovery correctness.
- Confirm that cache invalidation occurs synchronously within the publish transaction.
