# ADR-008: Managed Identity Provider (Supabase Auth) for Authentication and Backend RBAC

- **Status:** Accepted (revised)
- **Superseded in part:** ADR-011 selects self-hosting, backend-owned PostgreSQL role mapping, local JWT validation, email/password authentication, no MFA requirement, and no login/logout audit integration.
- **Date:** 2026-11-13
- **Supersedes:** The custom-built authentication decision originally recorded in this ADR on 2026-11-12.
- **Project:** University Transport Information Portal
- **Related drivers:**
  - **ASR-07 — Authentication and access control:** Students and the public read without authentication; only Transport Management and designated administrators, using individual accounts, may edit or publish.
  - **ASR-06 — Audit history and recovery:** Edits and publications must be retained in an auditable history for 30 days with actor attribution.
  - **ASR-03 — Draft/publish separation:** Only privileged users may publish route, schedule, and assignment changes; students must never see unpublished drafts.

## Context

The portal provides published transport information to students and the public without requiring authentication. However, editing and publishing transport data and announcements must be restricted to Transport Management and designated administrators.

These privileged users must have individual accounts so that their actions can be attributed to specific actors in the audit history.

The Authentication module is part of the backend modular monolith. The backend API must enforce role-based access control (RBAC), rather than relying on frontend restrictions.

The authentication approach must also support recording privileged-account login and logout events in the single append-only audit log, providing the required entry and exit points for audit purposes.

This ADR was originally accepted with a custom-built authentication decision. That decision is now revised: the team has approved adopting a managed identity provider instead, specifically to reduce the security and maintenance burden of building and operating credential storage, session handling, and account provisioning in-house, while keeping cost low given the small number of privileged accounts.

## Options considered

| Option | Advantages | Disadvantages |
|---|---|---|
| HTTP Basic Authentication | Simple authentication mechanism | Too weak and unauditable for individual-account and audit-attribution needs |
| Custom-built username/password authentication | Supports individual privileged accounts and allows login/logout entry and exit points to be recorded directly in the audit log | Adds significant security and maintenance burden (credential storage, hashing, session handling, account provisioning) that the small team must build and maintain |
| Firebase Authentication | Low setup effort, generous free tier, fully managed | RBAC requires custom claims managed outside the relational system of record; moderate vendor lock-in to the Google ecosystem |
| AWS Cognito | Native groups/roles, generous free tier | Heavier configuration effort; high vendor lock-in to the AWS ecosystem |
| **Supabase Auth** | Low-cost (generous free tier; flat-rate paid tier), low setup effort, hosted UI and SDKs, RBAC achievable via Postgres roles/row-level security alongside the existing relational system of record, open-source and self-hostable (lower lock-in), native Postgres-based audit/login logs available as a secondary signal | External dependency; requires a webhook/trigger integration to forward login/logout events into the system's own append-only audit log |

## Decision

Adopt **Supabase Auth as the managed identity provider** for privileged-user authentication, replacing the previously accepted custom-built authentication approach.

- Supabase Auth issues and manages credentials, sessions, and login/logout for Transport Management and designated-administrator accounts.
- The backend's Authentication module integrates with Supabase Auth (via its SDK/API) rather than implementing credential storage, password hashing, or session management itself.
- Privileged roles (Transport Management vs. designated administrator) are represented via Supabase custom claims or role metadata, which the backend Authentication module maps to internal RBAC roles.
- RBAC must still be enforced by the backend API itself (not solely by Supabase or by either frontend client) — Supabase authenticates the user; the backend authorizes the operation.
- Public read endpoints must remain unauthenticated.
- Login and logout events for privileged accounts must be captured (via Supabase webhooks/triggers) and recorded in the single append-only audit log owned by the Audit module.
- Login/logout audit entries must include actor attribution.
- No credential storage, password hashing, or session-management logic is to be built in-house.

## Rationale

Supabase Auth is selected because it is low-cost at this system's scale (a small number of privileged accounts well within its free tier, with a flat-rate paid tier if usage grows), has low setup effort (hosted UI and SDKs), and integrates naturally with the architecture's existing relational database as the system of record — simplifying the login/logout-to-audit-log integration this ADR requires. It also carries lower vendor lock-in than comparable managed options, since it is open-source and self-hostable if the team's needs change later.

HTTP Basic Authentication remains rejected: it is too weak and unauditable for individual-account and audit-attribution needs.

Custom-built authentication, the previously accepted option, is now rejected in favor of a managed provider: it added a security and maintenance burden (credential storage, hashing, session lifecycle, account provisioning) disproportionate to a small team's operational capacity, and that burden is better absorbed by a managed service purpose-built for it.

Keeping the Authentication module as the integration point (rather than embedding Supabase calls throughout the backend) preserves the modular monolith's internal responsibility boundaries. Enforcing RBAC at the backend API, in addition to Supabase's own authentication, ensures privileged operations remain protected independently of which frontend client makes the request and independently of Supabase-side role data alone.

Public read endpoints remain unauthenticated, preserving access for students and the public.

## Consequences

### Positive
- Privileged users have individual accounts without the team building credential storage or session handling itself.
- Login and logout events can still be recorded directly in the audit log, via webhook/trigger integration.
- Actor attribution supports accountability for privileged-account activity.
- Backend RBAC protects privileged operations independently of frontend behavior and independently of Supabase alone.
- Public read endpoints remain accessible without authentication.
- Reduced security and maintenance burden compared to custom-built authentication.
- Low cost at this system's scale, with a predictable flat-rate path if usage grows.

### Negative
- Introduces an external dependency on Supabase Auth for privileged-account login.
- Requires building and maintaining a webhook/trigger integration to forward login/logout events into the system's own append-only audit log.
- Role mapping (Supabase claims/metadata → internal RBAC roles) adds a configuration layer that must be kept correct and reviewed.
- Some vendor dependency remains, though mitigated by Supabase's open-source, self-hostable nature.

### Risks
- An outage of Supabase Auth would block privileged login (though public, unauthenticated reads are unaffected).
- Misconfigured role claims or row-level security policies could grant unintended access.
- Webhook delivery failures could cause missing login/logout entries in the audit log; a reconciliation or retry mechanism may be needed.
- Incomplete backend-side RBAC enforcement (relying on Supabase role data alone) would leave privileged operations insufficiently protected.
- Migrating away from Supabase later would require an account-migration plan.

### Open questions

The following details are **not yet specified** and must be confirmed before implementation:

- Whether Supabase Auth will be used as a managed cloud service or self-hosted.
- Exact mechanism and schema for mapping Supabase roles/custom claims to the two privileged roles.
- Mechanism for capturing login/logout events (webhook vs. polling Supabase's own logs) and forwarding them reliably into the audit log, including handling of delivery failures.
- Password policy, multi-factor authentication, and account lockout configuration within Supabase.
- Account provisioning, account changes, and account deactivation procedures for Transport Management and designated administrators.
- Exact audit-entry fields for login/logout events beyond actor attribution.
- Data residency or institutional compliance considerations relevant to using a third-party identity provider.

## Verification

- Verify that privileged-account authentication is handled by Supabase Auth, not by custom-built credential storage or session logic.
- Verify that individual accounts are used for Transport Management and designated administrators.
- Verify that RBAC is enforced by the backend API, not only by Supabase role data or either frontend client.
- Test that unauthorized users cannot edit or publish transport data or announcements.
- Verify that public read endpoints remain accessible without authentication.
- Verify that privileged-account login and logout events are recorded in the single append-only audit log.
- Verify that login/logout audit entries include actor attribution.
- Verify that login/logout events are retained consistently with the audit log's 30-day retention requirement.
- Verify that the webhook/trigger integration reliably forwards login/logout events, including behavior on delivery failure.
- Confirm that hosting mode (managed vs. self-hosted), role-mapping schema, password policy, and account-provisioning decisions are documented before implementation.
