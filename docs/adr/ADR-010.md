# ADR-010: Use a Relational Database as the Primary Data Store

- **Status:** Accepted
- **Current profile:** ADR-011 selects PostgreSQL and handwritten asynchronous SQL/migrations.
- **Date:** 2026-11-12
- **Project:** University Transport Information Portal
- **Related drivers:**
  - **ASR-03 — Draft/publish separation:** Route, schedule, and assignment edits must be saved as drafts and require a separate publish action. Public users must never see drafts.
  - **ASR-06 — Audit history and recovery:** Edits and publications must be retained in an auditable history for 30 days with actor attribution. Recovery is limited to previously published data, not drafts.
  - **ASR-01 — Publish-to-visible latency:** Published information must be visible/retrievable within 5 seconds at the 95th percentile, under a baseline of 500 concurrent users and 2,000 scheduled departures.

## Context

The portal manages structured transport information, including routes, schedules, assignments, announcements, feedback, and audit history.

The system must support versioned records, draft/publish separation, transactional publishing, audit history, and recovery of previously published data. It must also meet the publish-to-visible performance requirement.

The architecture must select a primary data store that supports these requirements while keeping the system manageable within the modular monolith.

## Options considered

| Option | Advantages | Disadvantages |
|---|---|---|
| Relational database | Supports structured data, transactions, and consistency requirements | Requires deliberate schema and query design |
| NoSQL database | Provides a flexible data model | Does not provide an identified advantage sufficient to justify replacing the relational approach for this system |

## Decision

Use a **relational database as the system of record**.

- The relational database is the primary persistent store for backend modules.
- Each module accesses its data through its own persistence responsibilities.
- Modules must not directly access another module's private database tables or internals.
- Both frontend clients communicate with the backend API; neither accesses the database directly.
- Versioned records must support draft/publish separation.
- Audit history must be stored in the append-only audit log.
- The database must support transactional edits, publishing, and audit writes.

The specific relational database engine is not yet selected.

## Rationale

A relational database provides the structured data and transactional behavior needed by the portal's transport information, versioning, publishing, and audit requirements.

The system requires draft/publish isolation and recovery of previously published versions. These requirements make consistent data handling important. A relational database provides the selected foundation for implementing these responsibilities within the modular monolith.

Using one primary database also avoids introducing additional database infrastructure without an ASR-based justification.

The database engine and detailed schema remain implementation decisions and must be confirmed before implementation.

## Consequences

### Positive
- Provides a single system of record for persistent application data.
- Supports transactional publishing and audit writes.
- Supports structured transport data and versioned records.
- Keeps persistence within the modular monolith's backend boundary.
- Avoids introducing additional databases without justification.

### Negative
- Requires deliberate schema design for versioning, draft/publish separation, and audit history.
- Modules must maintain clear ownership of their persistence responsibilities.
- Query and transaction design must support the required performance and consistency behavior.

### Risks
- Poor schema or query design could undermine the 5-second publish-to-visible target.
- Incorrect transaction handling could cause inconsistencies between published data and audit history.
- Direct access to another module's private tables could undermine modular boundaries.

### Revisit when
- The relational database cannot meet demonstrated performance, consistency, or recovery requirements.
- A specific ASR-based requirement justifies introducing another database technology.
- Independent data-storage requirements emerge that cannot reasonably be handled by the selected primary database.

## Verification

- Verify that the relational database is the system of record.
- Verify that both frontend clients access persistent data only through the backend API.
- Verify that modules do not directly access other modules' private tables or internals.
- Test transactional publishing and audit writing.
- Test draft/publish isolation and confirm public reads never expose drafts.
- Test recovery to previously published versions only.
- Measure publish-to-visible latency under the stated baseline of 500 concurrent users and 2,000 scheduled departures against the 5-second 95th-percentile target.
- Confirm that no additional database is introduced without an ASR-based justification and explicit approval.
