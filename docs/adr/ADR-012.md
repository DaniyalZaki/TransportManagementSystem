# ADR-012: Use Route-Level Weekly Schedule Rows

- **Status:** Accepted
- **Date:** 2026-11-21
- **Supersedes in part:** ADR-011 where it describes a recurring weekly row as selecting an individual bus.

## Context

The timetable needs a single schedule definition for a Route and departure
time, with every bus assigned to that Route shown together. Requiring an
operator to choose a bus again while adding a schedule row duplicates the
Route-to-bus assignment and can produce inconsistent schedule data.

## Decision

- A recurring weekly schedule row contains ISO weekday `1` through `7`
  (Monday through Sunday), Route, and PKT departure time.
- Route direction is constrained to `RETURN` or `PICK-UP`.
- A schedule row derives its bus set from the Route-to-bus assignments in the
  same change set; it has no independently selected bus identifier.
- Public schedule responses display the derived `bus_identifiers` collection.
  Current-departure responses remain Route–Bus entries because they represent
  the next departure for each assigned physical bus.
- A route-level schedule row with no Route-to-bus assignment is a publish
  warning. Publishing retains the existing explicit confirmation path.
- Partial date overrides remain Route–Bus–time operations because they address
  an individual physical service on one date.

## Consequences

This removes duplicated schedule input in the Admin Web App and makes the
public schedule show all buses serving a route at a time. Existing weekly rows
are migrated from weekdays `0–6` to `1–7`; their legacy bus column is retained
only for database compatibility and is not used to resolve new schedules.

## Verification

- Test that a route-level weekly row expands to every assigned bus.
- Test that public schedule output exposes all derived buses.
- Test accepted weekday bounds `1–7` and rejected out-of-range values.
- Verify the admin schedule editor has no bus selector and its table shows
  assigned buses.
