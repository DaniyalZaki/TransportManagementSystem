# ADR-002: Separate Public and Admin Clients

**Status:** Accepted
**Current profile:** ADR-011 limits privileged-account management to Transport Management; all other client-separation decisions remain in force.
**Date:** 2026-11-12
**Project:** University Transport Information Portal

## Related drivers

- **ASR-07 — Authentication and access control:** Public users must read information without authentication, while only Transport Management and designated administrators may edit or publish.
- **ASR-08 — Platform compatibility:** The client must support mobile, laptop, and desktop, with mobile prioritized.

## Context

The portal serves two distinct user groups: students and the public, who access transport information without logging in, and privileged users, who manage and publish transport data and announcements.

The architecture must provide public access while protecting administrative functionality. It must also support mobile, laptop, and desktop devices, with mobile prioritized.

The main architectural question is whether public and administrative functionality should be delivered through one unified application or through separate frontend clients.

## Options considered

| Option | Advantages | Disadvantages |
|---|---|---|
| Single unified app with route-based access control | One frontend application to build and maintain | Bundles admin code and weight into what students download on mobile; widens the public attack surface |
| Two separate frontend clients sharing one backend API | Keeps the public bundle lean and isolates the privileged surface | Requires two build pipelines |

## Decision

Adopt **two separate frontend clients**:

- **Public PWA:** Provides unauthenticated access to published transport information for students and the public.
- **Admin Web App:** Provides administrative functionality for Transport Management and designated administrators.

Both clients must communicate with the same backend API. Role-based access control (RBAC) must be enforced by the backend API, not by the frontend client.

Neither frontend may access the database directly.

## Rationale

A unified application would bundle administrative code and weight into the application downloaded by students, including on mobile devices. It would also widen the public attack surface.

Separate clients keep the public application lean and isolate the privileged administrative interface. Although this introduces two frontend build pipelines, the separation better addresses the different access requirements of public users and privileged users.

Enforcing RBAC at the backend API ensures that access control does not depend on frontend restrictions.

## Consequences

### Positive
- The Public PWA remains lean and does not need to bundle administrative functionality.
- The privileged administrative surface is isolated from the public-facing client.
- Public users can access published information without authentication.
- Both clients use one backend API, maintaining a common access boundary.

### Negative
- Two frontend clients require two build pipelines.
- Both clients must integrate with the same backend API.

### Risks
- If access control is enforced only in the frontend, privileged operations may not be adequately protected.
- If either client accesses the database directly, it violates the established architectural boundary.

### Revisit when
- The public and administrative client separation no longer meets the system's access or platform requirements.
- A reviewed architectural change provides an ASR-based justification for replacing the two-client approach.

## Verification

- Confirm that the Public PWA and Admin Web App are separate frontend clients.
- Confirm that both clients communicate only through the backend API.
- Verify that public read endpoints remain unauthenticated.
- Verify that privileged operations require authentication and that RBAC is enforced at the backend API.
- Confirm that neither frontend accesses the database directly.
- Test the client experience on mobile, laptop, and desktop, with mobile prioritized.
